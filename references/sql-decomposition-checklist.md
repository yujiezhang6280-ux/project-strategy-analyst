# SQL 拆解清单

用户提供 SQL 或询问 query 含义时，使用本清单。

## 目标

把 SQL 从语法翻译成业务逻辑：它测什么、粒度是什么、过滤了谁、join 如何改变行、最终指标能否相信。

## 检查清单

- 业务问题：SQL 试图回答什么？
- 基表：最底层事实表是什么？
- 行粒度：一行代表用户、订单、事件、session 还是别的？
- 时间范围：事件时间、支付时间、结算时间是否混用？
- join：每个 join 是扩行、过滤行还是补属性？
- 过滤：每个 `where` 条件对应什么业务范围？
- 去重：`distinct`、`row_number`、`group by`、anti-join 是否改变口径？
- 派生字段：是维度、标签还是指标？
- 聚合：在哪个粒度聚合？
- 指标：分子、分母、排除项和异常状态是什么？
- 中间结果：每个 CTE、join、过滤、去重和聚合后是否有行数或指标值可审计？
- 风险：是否可能与项目 `03-metric-logic.md` 冲突？

## 输出形状

```md
## SQL 目的

## 基表和行粒度

## Join 关系

## 过滤条件

## 指标逻辑

## 去重和聚合

## 数据审计轨迹

## 业务翻译

## 风险和定义缺口
```

## 数据审计轨迹

SQL review 不能只解释 query 意图，还要说明关键中间数是否可查。

建议输出：

```md
| SQL 步骤 | 行粒度 | 关键处理 | 期望审计数字 | 如果异常说明什么 |
|---|---|---|---|---|
```

审计数字包括：

- 基表输入行数、用户数、订单数或事件数
- 每次 join 前后的行数变化
- 每个过滤条件前后的保留率
- 去重前后数量
- 聚合后的分子、分母和指标值
- 最终输出与 dashboard 或官方口径的对账差异

如果用户没有提供实际执行结果，标记为 `需要跑数验证`，不要假装 SQL 中间值已经验证。

## 常见陷阱

- join 扩行后再 count，导致重复计算。
- 把事件数当用户数。
- 支付状态没有区分 attempt、success、refund、chargeback。
- 时间字段混用导致前后周期不可比。
- SQL 临时口径被误当官方指标。
