# 结构化思考与报告

用于报告、PPT 逻辑、老板汇报、结论、图表叙事和结构化分析输出。

## 原则

证据先于表达。不要让报告比分析本身更确定。

在选择图表、slide 结构、dashboard、notebook 或 BI 工具前，先定义决策问题。产物服务于判断，不是反过来。

## 结构

用户需要决策时，用结论先行：

```text
结论：
证据：
机制：
风险或边界：
下一步动作：
```

用户需要调查时，用问题解决结构：

```text
症状：
范围：
拆解：
发现：
未证明假设：
下一步检查：
```

## MECE 检查

拆解应当：

- 足够互斥，避免重复计算。
- 足够完整，能支持决策。
- 绑定指标、用户旅程或业务流程。
- 不比证据能支持的程度更细。

## QSCA / 5W2H 提示

这些是提示，不是必填标题：

- Question：核心问题是什么？
- Situation：当前背景是什么？
- Complication：发生了什么变化或不确定？
- Answer：应该相信什么或做什么？
- 5W2H：who、what、when、where、why、how、how much。

## 图表叙事

每张图或表都回答：

```text
发生了什么变化？
变化发生在哪里？
变化有多大？
哪个 segment 驱动？
什么解释被支持？
什么解释没有被支持？
下一步动作是什么？
```

## 可读 Markdown 文档

让 Markdown 像决策 memo，而不是聊天记录。

业务分析默认结构：

```md
## 结论
## Data Correctness（数据正确性）
## Data Audit Trail（数据审计轨迹）
## Driver Bridge（驱动项贡献拆解）或证据摘要
## 诊断
## 尚未证明
## 下一步检查
```

规则：

- 先给决策相关答案，不从背景铺垫开始。
- 标题要短，并保持并列。
- 优先使用 3-6 个一级 section，避免深层嵌套 bullet。
- caveat 要放在它限定的结论旁边，不只放到最后。
- 解释用短段落，比较和检查用表格。
- 如果输出会变成文档，细节前先给一行 executive summary。
- 指标波动、SQL review、dashboard review、业务诊断默认包含数据正确性表，除非用户明确要求简短回答。
- 只要结论依赖计算、桥接、比例变化、SQL 聚合或多步推导，就默认包含数据审计轨迹。
- 数据正确性回答“输入和口径能不能信”；数据审计轨迹回答“分析过程能不能复算”。

## 表格设计规则

当读者需要比较、贡献拆解、优先级、责任归属或检查清单时使用表格。需要推理的 prose 不要硬塞进表格。

表格前先说明：这张表要帮助判断或比较什么。

常用表格：

Driver Bridge（驱动项贡献拆解）：

```md
| 驱动项 | 上期 | 本期 | 变化 | 贡献 | 解读 |
|---|---:|---:|---:|---:|---|
```

Evidence Boundary（证据边界）：

```md
| 结论/判断 | 证据 | 置信度 | 尚未证明 | 下一步检查 |
|---|---|---|---|---|
```

Data Correctness（数据正确性）：

```md
| 检查项 | 当前状态 | 如果错误的风险 | 对结论的影响 | 下一步验证 |
|---|---|---|---|---|
```

Data Audit Trail（数据审计轨迹）：

```md
| 步骤 | 输入数字 | 计算/处理 | 输出数字 | 复算状态 | 备注 |
|---|---:|---|---:|---|---|
```

Action Plan（行动计划）：

```md
| 优先级 | 检查项 | 负责人/所需数据 | 为什么重要 | 输出 |
|---:|---|---|---|---|
```

格式规则：

- 表头带单位：`收入（¥）`、`转化率`、`变化（pp）`。
- delta 要带正负号：`+3.2 pp`、`-8.5%`、`-46k`。
- 按决策重要性或贡献大小排序。
- 表格尽量控制在 5-7 列；太宽就拆表。
- 不要把已观察事实和假设混在同一列。
- 行内包含解释判断时，增加 `证据`、`置信度` 或 `下一步检查`。
- 数据正确性行要包含 `如果错误的风险` 或 `对结论的影响`。
- 数据审计轨迹行要包含 `输入数字`、`计算/处理`、`输出数字` 和 `复算状态`。
- `pp` 表示百分点变化，`%` 表示相对变化。

数据正确性表应覆盖会让分析失效的风险：

- 指标定义和分母
- 时间粒度、时区和对比周期
- 实体粒度和去重
- 过滤、排除项、eligibility 和异常状态
- 数据新鲜度、迟到事件和缺失行
- join、归因、支付状态、退款或拒付逻辑
- 影响可比性的 segment mix 变化

数据审计轨迹应覆盖会让推导出错的环节：

- 原始输入数字、单位和周期
- 分子、分母和派生比率
- 绝对变化、相对变化和百分点变化
- driver bridge 每一步的输入、公式、输出和残差
- SQL 中每个 CTE、join、过滤、去重和聚合后的行数或指标值
- 无法复算的中间值要标为 `缺输入`，不能当作已验证
- 最后一行检查 reconstructed total 是否等于最终报告值；不一致时列出 residual

## Dashboard、Notebook 和 BI 输出

构建或修改数据产物前，写清：

```text
业务问题：
支持的决策：
指标粒度：
过滤和排除项：
比较逻辑：
预期动作：
```

只有指标粒度、过滤和比较逻辑清楚后，才选择视觉化形式。只保留能改变判断或动作的图表。

## 可审计产物选择

最终产物要方便复核，不只是方便阅读。

默认选择：

- 小数据优先用 Excel：适合单机打开、人工检查、公式可读、透视表或汇总表能承载的分析。
- 大数据优先用 Jupyter：适合多表 join、大量行、复杂清洗、统计检验、模型、循环计算或需要完整过程留痕的分析。

默认阈值：

- 小数据：原始数据通常不超过 100k 行，文件不超过 20 MB，计算逻辑可以在 workbook 内清楚表达。
- 大数据：超过上述规模，或即使行数不大但包含复杂 SQL、join、清洗、抽样、模型或多步推导。
- 用户指定 Excel 或 Jupyter 时，以用户指定为准，但要说明审计风险和补救方式。

Excel 产物规则：

- 尽量保留公式，不把派生指标只写成静态值。
- 能用 Excel 表、透视表、筛选、条件格式或数据验证表达的，就保留为可检查结构。
- 每个 workbook 至少包含：`README/说明`、`Source/原始数据或输入`、`Calc/计算过程`、`Check/校验`、`Output/结论`。
- 公式要引用输入单元格或命名区域，避免魔法数字。
- 关键指标旁边保留分子、分母、单位、时间范围和过滤条件。
- 透视表可用时优先使用；环境不支持原生透视表时，用可复算的汇总表和公式替代，并说明限制。

Jupyter 产物规则：

- 所有过程数据必须在 notebook 留痕，不能只输出最终结论。
- Markdown 说明、代码注释和检查说明使用中文；变量名、库名、SQL 字段名可以保留英文。
- notebook 必须能自上而下运行，除非数据权限或外部系统不可用，并明确写出阻塞点。
- 每一步都说明：目的、输入、处理、输出、检查点和风险。
- 对清洗、过滤、join、去重、聚合、抽样、统计检验、模型评估都保留中间行数或关键指标。
- 关键中间表要展示小样本、行数、字段类型、缺失率或聚合结果，避免只展示图。
- 最终 notebook 要包含 `数据审计轨迹`、`口径说明`、`中间结果索引`、`结论` 和 `复算/残差检查`。

如果同时需要业务汇报和过程复核：

- 大数据：用 Jupyter 作为主审计产物，必要时导出一个轻量 Excel 摘要给业务读者。
- 小数据：用 Excel 作为主产物，必要时附一个简短 Markdown 说明。
- 不要让 PPT 或老板摘要成为唯一产物；它们只能引用可审计的 Excel 或 Jupyter 结果。

## 报告质量规则

- 把决策相关结论放在最前面。
- 解释前先说明指标粒度和分母。
- 区分事实和解释。
- 证据不完整时写 caveat。
- 避免不会改变决策的装饰性框架。
- 避免不支持具体判断的装饰性图表。
- 下一步动作要具体。
- 扫描路径要明显：结论、数据正确性表、数据审计轨迹、证据表、边界、下一步。
- 表格用于降低理解成本，不用于掩盖弱证据。

## 常见输出形状

老板摘要：

```md
## 结论
## 依据
## 风险
## 下一步动作
```

分析报告：

```md

## 数据范围
## 发现
## 机制
## 限制

```
